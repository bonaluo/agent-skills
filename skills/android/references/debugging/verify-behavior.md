# 判读操作是否生效

这是整个调试流程里**最容易出错**的一环。注入一条手势只要一行命令，
判断它到底有没有生效却经常要花十倍的时间。

## 假阳性判据

**截图变了 ≠ 操作生效。** 异步内容（缩略图、网络图片、动画、时间显示）
本来就会改画面。用「截图 md5 变了」「两张图像素不同」当判据，
会得到大量假阳性，然后基于错误结论去改代码。

其它常见但不可靠的判据：

| 判据 | 为什么不可靠 |
|------|--------------|
| 截图 md5 / 像素差 | 异步内容随时会改画面 |
| 净位移等于预期值 | fling、回弹、惯性滚动都会让它失真 |
| 日志出现某条输出 | 可能来自上一次操作、或无关路径 |
| 界面"看起来一样" | 采样点太少，可能正好避开变化区域 |

## 选"只有该操作才能造成"的差异

优先用**语义判据**——那种别的原因解释不了的差异：

- **内容本身**：列表跳到哪一年、当前文件名是什么、标题栏文字是什么。
- **结构性变化**：某个分组头部有没有滚出屏幕、某个元素出现/消失。
- **数量级的跳变**：比如 400ms 内跨越了两年半的内容——
  只有"跳到指定位置"这类操作能做到，普通滑动不可能。

判断方法是反问自己：**还有别的什么原因能造成这个现象？**
如果答不上来，这个判据才可用。

## 排除惯性与回弹

- 快速滑动会触发 fling，多滑一段不可预测的距离。需要定量结论时，
  把速度压到 50dp/s 以下（见 [input-injection](input-injection.md)）。
- 滚动到底/到顶有回弹效果，位移会和手势距离不一致。
- **要断言"滚动了"而不是"滚动到某处"时，用语义判据代替位移判据。**

## 钉死初始状态

如果每次开始时的滚动位置、数据状态都不同，后面所有位移都失去参照。

- 用 `am force-stop` + 重新启动做冷启动（见 [build-and-install](../build/build-and-install.md)）。
- 截图确认起点，再执行操作。
- 必要时先把目标滚到一个确定位置（例如先滑到列表顶部），再开始测试。

顺带一个副产品：`force-stop` 后重启能验证状态**是否真的被持久化**——
如果重启后位置/设置还在，说明写进了存储，不是内存里的偶然残留。

## 一次只改一个变量

同时改了代码和操作方法，得到异常结果时无法归因。
每轮只变一件事，先确认基线可复现，再做对比。

如果一条命令的结果和预期相反、且反复无法解释，
**先怀疑注入方式**（`motionevent`、坐标偏移、时序），而不是应用逻辑。
