# 模拟器与真机的差异

## 模拟器缺什么

| 维度 | 差异 |
|------|------|
| 系统镜像 | 纯 AOSP 或 Google 镜像，**没有厂商 ROM**（MIUI / ColorOS / One UI 等） |
| 厂商应用 | 没有厂商相册、媒体库、文件管理器、安全中心 |
| ABI | 镜像多为 `x86_64`，真机多为 `arm64-v8a`；带 native 库（`.so`）的工程可能装不上或行为不同 |
| 传感器 | 摄像头是虚拟画面，无真实陀螺仪/GPS/光线传感器 |
| 通信 | 无 SIM、无真实通话与短信 |
| 渲染 | 软件渲染或宿主 GPU，与真机 GPU 驱动不同 |
| 性能 | **数值完全不可比**，慢十倍是常态 |

## 适合在模拟器上做的事

- 布局、主题、深浅色、横竖屏适配
- 业务逻辑、状态流转、导航栈
- 崩溃定位与堆栈复现
- 需要频繁重装、清数据、改分辨率的迭代
- 需要 `adb root` / `-writable-system` 的系统级调试
- 多版本/多分辨率矩阵（建多个 AVD 并存）

**优点**：可无界面运行、可快照秒开、可任意切换 API 级别、可 root、不占用户手机。

## 必须上真机的事

- **性能数据**：帧率、卡顿、内存占用、启动耗时、耗电。模拟器数值没有参考价值。
- **厂商适配**：厂商 ROM 的后台限制、权限弹窗差异、厂商相册/媒体库集成。
- **权限与后台**：各家的自启动、续航优化策略会杀掉后台进程，模拟器上不会出现。
- **native 库**：`.so` 的 ABI、NEON 指令集相关问题。
- **网络与真实数据规模**：几万张照片的媒体库、真实弱网。
- **输入法、分享、第三方 SDK 拉起**等依赖真实环境的能力。

## 给模拟器准备数据

模拟器的媒体库、下载目录默认是空的。推文件进去：

```bash
adb push photo.jpg /sdcard/Pictures/
adb push video.mp4 /sdcard/Movies/
```

**推完不一定立刻被系统索引到**（MediaStore 的感知方式随 Android 版本变化，
旧的 `MEDIA_SCANNER_SCAN_FILE` 广播在新版本上已受限）。
最稳妥的两条路：

1. 重启模拟器（慢但一定有效）；
2. 调用被测应用自身的"扫描/刷新"入口（顺带也测了这个功能）。

需要在模拟器上手工操作时，可以用 `input` 注入（见
[input-injection](../debugging/input-injection.md)），
无界面模式下照样有效。

## 快照带来的陷阱

AVD 默认会保存快照以便秒开，但这会让**状态跨会话残留**：

- 上一轮装的包、改的设置、推的文件都还在；
- 用 `-writable-system` 改过系统分区后，改动被写进快照，
  下次启动的系统状态和你以为的不一致；
- 验证"冷启动"相关行为时，快照会让它变成"热启动"。

**规则**：涉及系统改动或需要干净起点时，加 `-no-snapshot-load -no-snapshot-save`；
需要彻底重置时 `-wipe-data`。
